### Refactoring

**You own the contract. The structure changes; the behavior does not.** For "refactor", "rename", "extract", "inline", "dedupe", "restructure", "move this module", "tidy up this area". Distinct from Feature, which adds behavior, and Bug fix, which corrects it.

A refactor that smuggles in a behavior change loses its safety net. If the cleanup reveals a missing feature or a real bug, split it out and ship the structural change first against the pinned contract. A redesign is allowed, but name it and route to Feature. Large or cross-cutting structural work (a migration across many call sites, a coordinated reshape of many subsystems) belongs to the **forge-figure-it-out** skill; this playbook is the focused-to-medium change.

1. Pin the behavior contract first. Ask the orchestrator to select **forge-how** skill over the affected subsystem to learn the contract, then use an existing meaningful check, characterization test, snapshot, or equivalence harness that captures current behavior before any structure moves. The harness makes "refactor" a checkable claim (**forge-principle-prove-it-works**). For materially risky behavior, establish the pin before moving structure. For a low-impact mechanical change, use proportionate existing checks instead of a new harness that mirrors implementation.
2. Name the structure the code is missing per **forge-principle-model-the-domain**: a state machine over scattered booleans, a table or registry over spread-out branching, a typed model over repeated shape assumptions, a reducer over ad hoc mutations. Boring code stays when the shape is already clear and local; the reshape must delete branches or invalid states, not add indirection.
3. Name the target shape. State what the module layout, types, and call graph should be if built today (**forge-principle-foundational-thinking**, **forge-principle-redesign-from-first-principles**). If the target presents a consequential design choice, ask the orchestrator to select **forge-architect** skill for parallel design exploration of the shape before the move.
4. Subtract before you add. Delete dead weight, collapse one-caller wrappers, drop redundant validators, and remove orphan references before introducing the new shape (**forge-principle-subtract-before-you-add**). The smallest change that reaches the target shape ships (**forge-principle-laziness-protocol**). A speculative cleanup that "might help" gets reverted, not left to ride.
5. Move in small behavior-preserving steps, each keeping the pin green. For API reshapes, migrate every caller and delete the old API in the same wave (**forge-principle-migrate-callers-then-delete-legacy-apis**). Keep deliberate compatibility paths for published APIs, persisted formats, older clients and staged rollouts until migration evidence permits deletion. Spot-check every rename against the actual files; renames silently miss usages in strings, prose, and back-references. Request a bounded mechanical-edit assignment through the orchestrator when useful, using the `refactoring` role hint with a specific scope (file paths, the names being moved, the behavior to hold); review the diff yourself.
6. Prove behavior is unchanged on the real artifact, not "it compiles" (**forge-principle-prove-it-works**). For larger reshapes, run an equivalence check: a script that diffs old-vs-new outputs, a recorded baseline replayed against the new code, or a smoke run on the matching surface via the relevant control skill. Own the verification yourself; do not trust a delegate's "looks good" summary.
7. Confirm the change earns its place. The success measure is reduced reader load (**forge-principle-minimize-reader-load**): fewer layers between question and answer, less hidden state, fewer indirections without a second consumer. If the diff does not lower reader load somewhere, revert it.
8. Record coherent verified increments. With explicit history-edit and commit authority, prepare ordered commits that tell the story. A subtraction commit, then the reshape, then any follow-on cleanup, so a single revert undoes one slice. Shape them with the **sequence-verifiable-units** principle skill, so each behavior-preserving slice stays green before the next. Use **Opening a PR** only within publication authority.

**Reply:** the structure that changed, the pin you held it against, the equivalence proof, the reader-load delta, what shipped and what got reverted. No new behavior.
