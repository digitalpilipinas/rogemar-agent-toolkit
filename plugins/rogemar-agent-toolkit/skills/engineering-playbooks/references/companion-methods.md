# Portable companion methods

Use the original working companion skill when available. These focused methods
provide file/reasoning fallbacks for the same tasks when native bindings are
unavailable. Keep the current entry, orchestrator, task scope and acceptance
contract. A method does not authorize an extra provider, worker or side effect.

## Architect

Prefer one authoritative state owner and one supported path for each task. Keep
implementation internals private, generate repeated lists from one source, and
check drift when duplication cannot be removed. Migrate supported callers before
removing a legacy path; the presence of two adapters alone is not proof of waste.

Identify the material decision, consumers, constraints and uncertainty. Compare
credible alternatives against those constraints; prototype only a question that
evidence can resolve. Select and explain one proportionate design, recording
compatibility and reversal. Reuse an accepted architecture unless new evidence
changes it. Independent alternatives are optional and orchestrator-owned.

For changes to domain meaning, reuse create-plan's
[bounded decision and domain method](../../create-plan/references/task-framing.md#bounded-decision-questioning).

## Arena

Define equivalent inputs, a bounded question and an outcome-based comparison
before producing alternatives. Keep alternatives independent when authorized
capabilities permit; disclose when one agent develops them. Compare actual
artifacts, preserve counterexamples and choose one result. Do not call sequential
self-review an independent panel or change the rubric to favor an answer.

## Automate me

Turn explicitly requested working conventions into a personal mode skill. Inspect
the existing owner and current instructions, use only authorized history, preserve
settled preferences, and draft the smallest useful change. Reuse the applicable
authoring method and user approval. This is personal-style capture, not scheduling;
selection grants no history, persistence, global settings or publication authority.

## Blast radius

Trace changed interfaces through callers, stored data and operations. Identify
meaningful failure cases and the checks needed for affected consumers. Inspect
the actual candidate, keep findings grounded, and avoid an unrelated whole-system
audit. Recheck the affected boundary after the fix.

## Bro

Use the conversational style requested by the user. Discuss the immediate problem
plainly and preserve factual uncertainty. Do not change task ownership, adopt an
unrequested persona or turn conversational support into implementation authority.

## Create verification skill

Find existing verification before adding a recipe. For a recurring coverage gap,
name the observable behavior, prerequisites, driver, failure cases, artifact and
cleanup. Implement the smallest reusable recipe in the current verification
owner. Keep it draft until an actual authorized execution proves it.

## Figure it out

Reuse the accepted outcome, task IDs and evidence trail. Identify the next
uncertainty, choose a bounded change or experiment, inspect its real result, and
retain or reverse the task-owned change. Scale verification to consequences.
Continue authorized work; surface only material unresolved scope or authority.

## How

Start at the relevant entry point. Trace data, state transitions, calls and failure
paths in current source and tests. Explain the smallest complete mechanism with
source pointers and uncertainty; run a permitted targeted probe only when needed.
Do not confuse reading a test with executing it.

## Interrogate

Adversarially review the stated code, diff or design against its intent. Trace
material claims through contracts and callers; distinguish defects from preferences.
Use independent read-only reviewers only when justified and available through the
existing orchestrator, then reconcile a single evidence-backed verdict. Disclose
single-agent coverage. Review grants no fix authority. Use create-plan for ordinary
requirements clarification, not this review method.

## Maintain verification skill

Compare the existing recipe with changed behavior, drivers and prerequisites.
Repair the affected contract, preserve intended behavior, and rerun the useful
case when authorized. Record unchanged-with-reason or a remaining gap. A focused
repair does not certify unrelated features or the entire map.

## Make bot ui

Define the human interaction and the actual agent operations it exposes. Discover
available native adapters; implement only supported bindings and authorization.
Show progress, results and recoverable errors clearly. Test the real interaction
and keep unavailable backend actions visibly unavailable.

## No comments

Review comments beside the code they describe. Improve names or structure where
that removes repetition; keep rationale, invariants, compatibility explanations,
licenses and safety constraints that code alone does not express. Verify changed
behavior if cleanup affects executable code.

## Recall

Read only the supplied or authorized task/topic/history window. Recover the goal,
decisions, candidate, authority, unfinished work and evidence references. Refresh
volatile branch, file, permission and runtime facts before reuse. Avoid broad
private-history searches and never promote an old summary above current evidence.

## Reflect

Compare an observed result with its intended outcome. Classify implementation,
environment, verifier, context, routing and authority causes before proposing a
lesson. Prefer a regression or structural prevention where useful. Route an
evidenced candidate to the existing Project Learning writer when enrolled;
reflection does not approve a global instruction change.

At a verified milestone with meaningful friction, inspect the actual session's
navigation, environment, tooling, broken or unwired checks and repeated mistakes.
Prefer repairing an existing check or pointer before adding instructions. Compare
the prevention cost with the observed problem; no finding or retro report is
required when there is no useful lesson. Keep broader changes as proposals and
apply small corrections already covered by task authority. Project Learning's
enrollment, candidate review and promotion boundaries remain intact.

## Setup

Inspect the active harness's Forge model/profile preferences and observed native
controls. Codex uses forge-setup and plan-model-router; Cursor uses cursor-forge-setup;
other harnesses use their supported controls or retain native defaults. Preserve
user choices and governing limits. A saved preference is not a live model switch.
Use codex-capability-maintainer for general capability preparation. This method
grants no installation, credential, provider or configuration authority.

## Show me your work

Use the current task's authoritative evidence record. Capture the material
hypothesis or decision, experiment, result, candidate and next action. Link the
underlying artifact rather than copying a transcript. Export a table only when
useful; do not create a competing mandatory log or publish private evidence.

## Swarm

Identify independent coverage questions that earn the cost of delegation. The
existing orchestrator checks authority, available workers, resource conflicts and
bounded assignments. Reconcile actual outputs and unresolved gaps. With one
agent, perform useful checks sequentially and disclose the absence of independence.

## Tdd

Use when TDD/regression testing is explicitly requested or a bug has an obvious
cheap local test target. Reproduce the intended behavior with a meaningful failing
check, fix the defect and re-run relevant coverage. If the test would require broad
unrelated setup, explain the practical limit and use the closest useful verification.
Do not weaken existing assertions or force tests that mirror the implementation.

## Teach

Infer the learner's immediate question and explain the smallest complete answer.
Use How for mechanism and Why for rationale only when needed. Preserve confidence
qualifiers. Add a diagram, example or visual when it improves understanding;
there is no fixed visual count, image requirement or parallel-agent requirement.

## Technical writing

Identify the reader's task and lead with the outcome or required action. Use
concrete terms and ordered steps with clear prerequisites and failure recovery.
Check examples and references. Remove repetition while retaining material
constraints; respect the user's style and the source's factual uncertainty.

## Typescript best practices

Follow the project's existing types, compiler settings and public contracts.
Model relevant state and validate untrusted boundaries; avoid widening types or
assertions that conceal errors. Use the affected typecheck and behavior tests.
Do not introduce a framework, type layer or full audit merely for reading a file.

## Unslop

Edit requested prose for clarity, specificity and economy. Preserve factual meaning,
technical constraints, licenses and the user's voice; remove repetition and unsupported
claims. Inspect the actual text and relevant source references. This is not an
unrequested code cleanup or permission to invent a different voice.

## Why

Start with the scoped question and relevant current source, commits and design
records. Search only authorized additional sources when they can resolve the
uncertainty. Separate documented intent, supporting evidence and inference;
preserve contradictory evidence and confidence qualifiers. Missing history means
unknown rationale, not permission to invent it.
