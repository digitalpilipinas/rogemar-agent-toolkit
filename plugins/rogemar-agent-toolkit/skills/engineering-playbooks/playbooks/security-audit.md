# Scoped security review and optional comprehensive audit

The existing review owner remains responsible for findings and reconciliation.
Select this method for an explicit security assessment; do not activate every
companion on every edit or create another coordinator. The toolkit supplies a
method, not an installed vulnerability harness or verified universal sandbox.

## Choose the scope

A focused question uses only the relevant boundary and current task record.
A comprehensive audit needs an explicit target, revision, coverage boundary,
permitted techniques, evidence destination, resource budget and stop conditions.
File/report creation follows actual authority. Missing scope for intrusive actions
blocks those actions, not read-only analysis already authorized.

## Inspect, investigate, refute

Map relevant identities, protected resources, entrypoints, transformations,
capability grants and sinks. Choose domain lenses from actual boundaries: web/auth,
AI tools/memory, native/mobile/IPC, data lifecycle, cloud, supply chain, protocols,
and resource exhaustion. A dependency name alone does not justify a whole domain.

Reuse one existing coverage record with stable source-derived units. Record actual
reviewed paths and checks, including blocked, deferred and out-of-scope work. Scope
selection or agent count is not coverage. Check related retry, resume, cancellation,
batch, fallback and legacy paths where they can reach the same effect.

Investigate from a concrete security invariant. Inspect the strongest preventing
control. Give consequential candidates to an independent permitted verifier that
tries to disprove the claim. Initial investigators do not share preferred findings;
a verifier receives the candidate but not another verifier's verdict. Distinguish
established vulnerabilities, exact needs-validation leads, rejected claims, and
hardening opportunities. Preserve the repository's priority terminology.

## Safe execution and artifacts

Untrusted target-controlled processes require real OS-enforced isolation, a minimal
allowlisted environment without real credentials, bounded CPU/memory/process/disk/
wall-clock use, confined scratch writes, and restricted networking. Use synthetic
principals and stop at the minimum safe observable effect. Do not install packages,
probe live/shared endpoints, spend provider quota, or run an exploit just because a
review method suggests it. Approved development runs have their own distinct scope.

The trusted host must collect predeclared bounded regular-file evidence after child
processes terminate. Reject escaping paths, symlinks, devices, sockets, FIFOs,
hard-linked/changing files, and unsafe archives. Do not expose retained artifacts or
other workers' directories to the target. A written rule does not enforce these
controls. Missing required isolation or safe evidence handling leaves execution
blocked and the decisive claim unverified.

## Bound the work and close honestly

Reserve capacity for refutation, final integration and reporting before hunting.
Scale breadth rather than quietly lowering a required evidence bar. No fixed agent
count or endless clean-critic loop is required by this portable adaptation. If an
explicitly selected provider workflow has stricter requirements, preserve them or
report that its full procedure was not completed.

Revalidate changed source and decisive runtime conditions. An unchanged rejected
claim can be suppressed, not its entire coverage unit. Preserve unresolved coverage
when a budget expires. Report zero established vulnerabilities when that is the
result; do not pad the report with invented low-severity defects. Keep actual
execution and source-only evidence separate. Security-method availability is not
ASVS or other assurance certification.
