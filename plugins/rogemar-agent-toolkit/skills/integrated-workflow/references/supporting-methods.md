# Conditional supporting methods

Read only the applicable section. The existing orchestrator owns selection and
dispatch; these methods do not add a second plan, ledger or mandatory reviewer.

## Scope, navigation and completion

For substantive programmes with authorized available independent workers, reuse
one read-only reviewer for scope and unnecessary complexity at material package
activation and pre-acceptance. Combine with appropriate correctness/counterexample
coverage when its contract permits; do not create a reviewer per helper or poll
unchanged work. Without a worker, the parent audits scope and reports any explicitly
required independence as unmet. Apply the same necessity/effort rule to implementation
and QA packages; do not test speculative support or remove requested safeguards.

Use `agent-map` for unfamiliar architecture, multi-file impact or caller tracing.
Check freshness, make one targeted query, then verify against source/tests. Skip
known-file work. Refresh generated metadata only within task scope and worktree
hygiene; otherwise use `rg`. Do not install hooks, alter ignore rules or commit map
output implicitly. Missing/stale edges are unknown, not proof of no callers.

Use `unlazy` only when justified by its
[First-Time-Right Delivery adapter](../../first-time-right-delivery/references/unlazy.md).
Check the installed version and reuse the approved plan/acceptance record. Abandoned,
deferred and blocked gates are not passed gates; measure report claims against the
candidate. It creates no second programme, worker hierarchy, hook or install requirement.

Apply the [automatic verification and learning checkpoints](../../engineering-playbooks/references/agent-friendly-workflow.md)
at start/resume, affected behavior, acceptance and completion. Reuse a project verifier;
create only missing authorized coverage. Use full maintenance for a due full map audit,
not every small fix. During frozen QA do not refresh generated navigation metadata.

Read accepted project lessons when relevant. `project-learning` captures only on
explicit request or an explicitly enrolled workflow completion checkpoint; pending
candidates remain inactive. Enrollment does not authorize promotion, shared-skill
edits, memory writes, hooks or background collection. Capture failures are nonblocking.

## Ponytail

Use through the current minimality owner when installed and useful. Select only
one applicable method; never install/vendor its external plugin implicitly.

- `ponytail`: challenge speculation, trace callers and prefer existing code,
  standard-library or native features before new custom abstractions/dependencies.
- `ponytail-review`: scoped complexity evidence in the same finding ledger, not
  correctness/security/merge approval.
- `ponytail-debt`: on an explicit debt-report request, collect existing shortcut
  markers and revisit triggers. Reuse existing records; do not insert markers
  merely to populate a new ledger.
- `ponytail-audit`: separately requested whole-repository audit; ordinary PR work
  does not authorize this expansion or automatic sprint additions.
- `ponytail-gain`: benchmark display only when requested. Published figures do not
  measure this project's savings or delivery quality.

Simplicity preserves requested behavior, trust boundaries, data protection,
accessibility and required checks. Terse output, fewest lines or one-test preferences
cannot override the acceptance contract. Do not silently persist a mode across tasks.

## External review providers

Additional terminal providers are optional unless named as required at a boundary.
Use the exact approved providers/models and authorized data/usage scope through
`agent-collaboration-terminal`; never silently substitute a provider/model. Review
the frozen integrated candidate with exact allowed/excluded paths and artifacts
outside the repository. All findings remain advisory until validated against the
actual code and executable checks. CodeRabbit and GitHub Codex remain separate
parent-owned evidence layers, never nested actions inside another provider.

Prefer the terminal skill's managed-background/manual-approval profile with visible
fallback unless a visible interactive session is explicitly required. Pass its
opt-in `--review-profile code` only for a task that actually reviews code, a diff,
branch or PR; `--mode review` alone does not activate that profile. For
`needs_attention`, use the recorded fallback once when already authorized, verify
native-CLI readiness and only then submit the frozen prompt. Shell creation,
CLI readiness, prompt submission and completed review are distinct evidence states.

Every selected terminal code reviewer performs a full independent review of the
agreed candidate, including the whole in-scope diff and relevant callers/tests.
Complementary emphasis does not narrow that coverage: Antigravity for broad
quality/test gaps; Grok for trust boundaries, privacy,
authorization, architecture and minimality; Cursor for navigation, maintainability
and user reliability; Junie selectively for reproduction/runtime/test evidence.
These are methods, not automatic assignments or mandatory model choices. Parallelize
only independent read-only reviews under the current orchestrator.

Do not substitute a sampled, light, findings-only or single-axis pass for a
selected provider's full review. Keep allowed/excluded paths and provider authority
intact; missing required coverage is partial evidence, not a silently smaller
review. This changes review depth, not invocation cadence or provider selection.

GitHub Cloud Antigravity is a separate PR-native app. Only when installed,
authorized, named in the controls and due on a ready PR may it be requested.
Reuse equivalent automatic evidence already queued, running or completed. If all
those prerequisites hold and no equivalent review exists, post one authorized
top-level head/scope/validation update and the exact standalone command below.
Otherwise record unavailable or not applicable as appropriate without posting:

```text
@agy /review
```

Wait for its actual review submission, state and check annotations; the command
means requested, not passed. Do not route the app through a terminal executable or
duplicate a review already queued/running/completed for the same valid scope.
An unavailable required app blocks its named boundary; optional failure stays optional.

The parent discovers capabilities surfaced in its harness; each authorized provider
may inspect its own installed/native skills, tools, MCPs and plugins within the
frozen assignment. Neither tier searches the external marketplace, installs,
authenticates or expands approved workspace/data/credit/action authority. A named
skill is not proof of a callable tool. Provider-native judgment remains within the
assigned scope and feeds the same consolidated finding and convergence process.

## PR helper skills

When `autopilot` or `autofix` assists an active ready-PR cloud wave, it consumes the same
[cloud barrier and allowance](coderabbit-review.md#ready-pr-coderabbit-and-codex).
Its polling or comment-processing loop cannot launch a separate review cycle,
reset counts, or validate/fix one cloud provider's feedback while the other is
pending. Preserve each helper's standalone scope and authorization boundaries.
Do not assume a push triggers review or promise a fixed completion time; inspect
configured triggers and actual provider status. Runtime-owned helper packages
remain external dependencies, with this maintained adapter governing integration.
