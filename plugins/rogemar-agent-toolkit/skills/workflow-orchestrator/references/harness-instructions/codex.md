# Codex adapter

Use only with the shared working instructions in Codex. The user-global entry is `~/.codex/AGENTS.md`; repository root/nested AGENTS files retain project authority. Compose the core and this adapter as ordinary text; do not assume Claude-style imports are supported. Preserve local-only/private material and native approval controls.

Use installed skills through the actual Codex invocation route. A pasted role or command is not dispatch proof. `workflow-orchestrator` owns dispatch; no additional coordinator or persistent mode is implied.

## Model routing

Without a named Codex Forge mode, the manually selected parent model and reasoning
are independent ceilings for native Codex workers. Choose the lowest sufficient
available profile within those limits; report ceiling constraints or unavailable
identity honestly and keep unresolved work with the main agent when necessary.

For Codex work with an explicitly selected Forge mode (`default`, `peak`, `balanced`,
`lean`, `economy`; legacy aliases `supreme`, `optimize`, `budget`, `sprint`), the mode's permitted
profiles remain subject to the actual accepted parent's model and reasoning
ceilings and the mode's limits. Only qualified hard-role exceptions in the router
may exceed normal ceilings. Reconcile a different desired parent through the
router's accepted-fallback or verified-switch procedure before dispatch; report
unsupported profiles instead of bypassing qualification. Explicit user limits
and actual runtime availability still apply. `workflow-orchestrator` owns dispatch and
`plan-model-router` qualifies every justified Forge worker assignment. Keep the
model catalog, role mappings and resolver details in the router skill.

A requested parent change must use a supported current-task control and be
verified. Otherwise report it as unapplied with the required manual action.
Preferences, worker spawns and self-reported identity do not prove a parent switch.
Use the shared Forge mode/status contract when Forge is active; do not infer a
mode from the parent or prompt for one during unrelated setup inspection.

Outside Forge, use the appropriate harness router for multi-increment, multi-PR
or materially mixed-risk planning when installed. In other harnesses, retain
parent ceilings unless an explicit applicable user policy grants a native mode
exception; use observed native controls and never import Codex model IDs. Models
cannot substitute for required tests, independent review or authority.

Use supported scheduling only for explicitly authorized ongoing work. Preserve the task's quiet-notification preference, cadence, target, existing monitor and stop conditions. An instruction file does not apply a live profile, permission, parent switch or automation.
